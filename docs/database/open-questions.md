# MatchIQ — схема БД: решения и открытые вопросы

**Статус:** вопросы по доменной схеме закрыты — пользователь принял **все предложения по умолчанию** (2026-11-25); их можно скорректировать на реальных данных (см. «Пересмотр после реальных данных»). Решения по мультиязычности и производительности № 27–28 приняты ранее; вопросы № 29–35 приняты по умолчанию 2026-11-25. Контекст — [README.md](README.md), [schema.md](schema.md), [formats.md](formats.md), [i18n.md](i18n.md), [performance.md](performance.md). Миграции и Eloquent-модели созданы 2026-11-25 (`web/database/migrations`, `web/app/Models`).

## Принятые решения

| Решение | Суть | Где отражено |
|---------|------|--------------|
| **Стыки — этап сезона турнира** | Стыковые матчи (РПЛ/ФНЛ и подобные) — этап `stages.type = playoff` **внутри сезона** соревнования, а не отдельное соревнование. Матчи пишутся с `competition_id` этого турнира, участники из другой лиги входят через `stage_teams`; очки стыков в таблицу `league` не идут | [formats.md](formats.md#3-чемпионат--стыковые-матчи), [schema.md](schema.md#1-география-и-соревнования) |
| **Товарищеские — вне MVP** | `competitions.type = friendly` и `stages.type = friendly` остаются в модели как **задел**, но в первых миграциях и в MVP не реализуются. Прогнозы по ним в будущем считать можно. Правило picks/рейтинга для товарищеских **не зафиксировано** (пользователь уточняет) | [formats.md](formats.md#4-товарищеские-матчи-вне-mvp) |

## Решения по умолчанию (приняты)

Ниже — вопросы, которые обсуждались, и **принятый по умолчанию ответ** (правая колонка). Это рабочие решения для первых миграций; правки допустимы после проверки на реальных данных источника.

| # | Вопрос | Принято (по умолчанию) |
|---|--------|------------------------|
| 1 | **Club vs team.** В URL и UI — «клуб» (`/clubs/{id}`), в модели — `teams`. Нужны ли сборные (UCL их не требует, но ЧМ/ЧЕ потребуют)? | Одна таблица `teams` с `type: club \| national`; URL остаётся `/clubs/{id}` для клубов, для сборных позже `/teams/{id}` или тот же роут. Дубли/молодёжка — `parent_team_id`, в РПЛ не участвуют |
| 2 | **Форматы соревнований.** Схема покрывает чемпионат, кубок, чемпионат + стыки, товарищеские, UCL, ЧМ, две группы, чистый плей-офф ([formats.md](formats.md)). Подходит ли разбиение на `stages` (`league` / `group` / `knockout` / `playoff` / `friendly`) + `ties` с `legs = 1 \| 2`, и достаточно ли `matches.tie_id` + `leg` для двухматчевых пар? | Да: плей-офф всегда через `ties`, даже одиночные матчи; формат меняется по сезонам набором этапов; правила (выездные голы, доп. время, пенальти, тай-брейки) — в `stages.rules` jsonb |
| 3 | **Хранение xG.** Достаточно агрегата по матчу/периоду или нужны удары (shot map)? Есть ли xG в выбранном источнике, или считаем сами? | MVP: `xg`, `xga` в `match_team_stats` (по периодам) и `xg`, `xa` в `match_player_stats`; shot-level (`match_shots`: минута, игрок, xG, исход, координаты) — позже, когда источник отдаст. Если источник без xG — поле NULL, UI показывает «–» |
| 4 | **История рейтинга.** Достаточно окон над `picks` (неделя / месяц / сезон / всё время) или нужна история мест и очков по дням (график, «прошлое место»)? | MVP: только `leaderboard_entries` с `period_key` (срезы закрытых периодов остаются как архив). График и ежедневный снимок — позже отдельной таблицей `rating_daily_snapshots`. Ledger очков (`points_ledger`) не вводим: источник правды — `picks.points` |
| 5 | **Таблица: хранить или считать.** Согласны с материализованными срезами `standings` по турам? Нужны ли штрафные очки/снятие очков и тай-брейки по личным встречам в MVP? | Хранить срезы (см. [schema.md](schema.md#4-турнирные-таблицы)); тай-брейки в `stages.rules` реализуем только «очки → разница → забитые», остальное — по необходимости; `points_adjustment` в `stage_teams` — позже |
| 6 | **Денормализация `matches.season_id` / `competition_id`.** Дублируем ради быстрых выборок («лига + день») или всегда джойним через `stage`? | Дублируем оба поля, поддерживаем сервисом записи (и проверкой в тестах); без триггеров БД на старте |
| 7 | **Сезоны: свои на соревнование или общий справочник «годов».** РПЛ «2026/27» против лиг календарного года (ЛС, МЛС). | `seasons` принадлежит `competition`, `slug` свободный (`2026-27`, `2026`); общий справочник не нужен |
| 8 | **Статистика игроков/команд: колонки или key-value.** Источник может отдавать разный набор метрик. | Ядро — колонками (быстрые агрегаты для таблиц лидеров), хвост — `extra jsonb`. Новую метрику, нужную UI для сортировки, выносим в колонку миграцией. Альтернатива — `stat_types` + long-format; пока не нужно |
| 9 | **Рынки: фиксированный каталог или произвольные линии.** Нужны ли фора, индивидуальные тоталы, угловые на периоды в MVP? | Каталог в `market_types` расширяем сидером; `line` в `prediction_outcomes` позволяет любые линии (1.5 / 2.5 / 3.5). MVP: исходы, тотал голов, обе забьют, двойной шанс, тайм/матч, ТБ/ТМ угловых и ЖК |
| 10 | **Вероятности: целые проценты или доля.** UI показывает целые, пары суммируются в 100 — округление считаем на бэке (largest remainder) или на фронте? | Храним долю `numeric(5,4)`; целые, суммирующиеся в 100, готовит бэкенд (resource), чтобы ничего не расходилось между главной и матчем |
| 11 | **Pick: заменять до kickoff.** История замен нужна или только последний выбор? | Хранить историю (`superseded_at`, partial unique на активный). Если не нужно — просто UPDATE строки, схему можно упростить |
| 12 | **Никнейм.** Уникальный `users.name`? Кириллица, пробелы, регистр? | Добавить `users.nickname`-политику отдельным решением: уникальность case-insensitive (`citext`/lower-index), 3–24 символа; в URL — только `users.id`. Сейчас `name` не уникален |
| 13 | **Конфликт источников.** Если два провайдера отдают разные счёт/составы, кто выигрывает? | `competition_sources.priority` + правило «побеждает провайдер с меньшим priority; ручная правка (`manual`) всегда выше»; хранить per-field provenance не будем |
| 14 | **Несматченные сущности.** Как работать с новой командой/игроком без маппинга? | Коллектор создаёт запись «на ревью» (`external_ids.matched_by = 'auto'`, флаг в `meta`) и пишет в `ingestion_runs.stats`; ручное слияние — позже в админке, до неё — SQL/artisan-команда |
| 15 | **Игроки по сезону.** `squad_memberships` по датам vs «заявка на сезон» (`team_id`, `season_id`). Нужны ли договоры/трансферы? | Даты-периоды (проще для трансферов позже); «состав на сезон» получаем пересечением с `seasons.starts_on/ends_on`. Договоры, суммы трансферов — вне MVP |
| 16 | **Комментарии.** Нужны ли в первой версии БД (в макете демо-тред)? | `match_comments` — «позже»; в первых миграциях не создаём |
| 17 | **Хранение сырых ответов источника** (для отладки и повторного разбора) | Не в Postgres (или с retention 7–14 дней); решить вместе с реализацией Go collector |
| 18 | **Часовые пояса и «день» на главной** (Вчера / Сегодня / Завтра). Чей часовой пояс определяет «сегодня»? | `kickoff_at` в UTC; день для фильтра считается в таймзоне продукта (Europe/Moscow для РПЛ) параметром запроса; пользовательская таймзона — позже |
| 19 | **Мок → БД.** Моковые id клубов (1–16), турнира РПЛ (`id = 1`), игроков рейтинга (`1 000 000+`). Сохраняем ли их как реальные id при сидировании? | Сидер создаёт РПЛ с `id = 1` и 16 клубов с id 1–16 (чтобы ссылки/тесты не ломались); игроки рейтинга `1 000 000+` в БД не переносятся, моки остаются только в тестах до полного перехода |
| 20 | **Товарищеские (вне MVP): picks и рейтинг.** Прогнозы по товарищеским считать можно; идут ли picks по ним в рейтинг — правило пользователь ещё уточняет | Принято: ничего не реализуем (товарищеские вне MVP), задел в модели есть (тип `friendly`). **Правило рейтинга пока не фиксируем** — решим вместе с включением товарищеских. Если понадобится исключение из рейтинга — флаг на `competitions` (например `rating_enabled`) без смены схемы матчей |
| 22 | **Отборочные раунды** (квалификация UCL/ЧМ). | Вне MVP; когда понадобится — этапы `knockout` / `group` в том же сезоне перед основным или отдельное соревнование `*_qualification` |
| 23 | **Перенос очков между этапами** («чемпионская группа», половина очков). | `stage_teams.initial_points`; формула переноса — в `stages.rules`, считает сервис при создании этапа |
| 24 | **Правило определения победителя пары** (выездные голы, доп. время, пенальти) меняется по турнирам и годам. | Флаги в `stages.rules`, итог пишется в `ties.decided_by`; логику правил держим в одном сервисе, не в SQL |
| 25 | **Генерация сетки плей-офф.** Создаёт ли коллектор все пары заранее (с `source_a/source_b`) или только когда известны обе команды? | Заранее создаём `ties` с заглушками (для UI-сетки); `matches` — только когда обе команды определены |
| 26 | **Лиговая фаза UCL (одна таблица на 36, неполный круг)** — отдельный тип этапа или `league` с `matches_per_team`? | `league` + `stages.matches_per_team = 8`, `stage_group_id = NULL` |
| 27 | **Мультиязычность сущностей.** Как хранить переводы имён клубов, лиг, игроков, судей, тренеров, стадионов, стран, чтобы не перегружать запросы? | **Гибрид:** каноническое английское имя в `name`, переводы в **jsonb `name_i18n`** на самой сущности (`{"ru": "Зенит"}`; у `teams`/`competitions` ещё `short_name_i18n`, у `teams`/`venues` `city_i18n`); ключ `en` не пишется; чтение `name_i18n[locale] ?? name` без JOIN, выбор языка при сериализации, кэш локаленезависимый. Коллектор пишет только `name` и не трогает `*_i18n`; ИИ заполняет только пустые ключи. Колонок `name_ru`/`label_ru` нет. Таблица `entity_translations` (провенанс, ревью, длинные поля) — позже как write-side, jsonb станет проекцией. Подписи этапов/туров — языковые файлы приложения по `type`/`code`/`number`, не данные. Подробно — [i18n.md](i18n.md) |
| 28 | **Производительность при большом объёме.** Что материализуем, кэшируем, индексируем; партиционируем ли `matches`? | Материализуем `standings` (+ `is_current`), `leaderboard_entries`, **`player_season_stats`** (лидеры; `team_season_stats` — позже), заголовок прогноза `match_predictions.p_home/p_draw/p_away`; Redis: лента, матч, таблицы, лидеры, счётчики picks (ключи без локали); индексы — partial по `status` (`live`/`scheduled`/`finished`), `(competition_id, kickoff_at)`, H2H-выражение, covering для рейтинга; keyset-пагинация, бюджет запросов на страницу (главная ≤ 5, матч ≤ 8), `preventLazyLoading` и тесты на число запросов; политика хранения устаревших `pre_match`-прогнозов. **Партиционирование в MVP не делаем** (ограничение PK/FK); по порогам: сначала дочерние таблицы `HASH (match_id)`, `matches` по `kickoff_at` — в последнюю очередь. Подробно — [performance.md](performance.md) |

## Мультиязычность и производительность (№ 29–35)

**Приняты по умолчанию — 2026-11-25** (пользователь подтвердил все предложения ниже). Правки допустимы после проверки на реальных данных.

| # | Вопрос | Принято (по умолчанию, 2026-11-25) |
|---|--------|-------------------------------------|
| 29 | **Источник без английских имён.** Если парсер отдаёт только русские названия («Зенит»), откуда брать каноническое EN-имя? | `source_providers.config.source_locale`; коллектор пишет полученное в `name` как временное значение и (если локаль не `en`) дублирует в `name_i18n[source_locale]`; в очередь ревью новых сущностей (п. 14) добавляется шаг «задать EN-имя» (вручную или ИИ); `slug` создаётся после EN-имени |
| 30 | **Набор локалей в UI MVP и выбор языка.** | MVP: интерфейс `ru`, fallback `en`; колонки готовы к `es` и др. Локаль запроса: `users.locale` → cookie → `Accept-Language` → `ru`; URL без языкового префикса (пересматриваем при SEO) |
| 31 | **Провенанс и ревью ИИ-переводов.** | В MVP не ведём: ИИ заполняет только пустые ключи, правки вручную имеют приоритет. Если понадобится «кто/когда/проверено» — вводим `entity_translations` как write-side |
| 32 | **Поиск по переводам** (искать «Зенит» при EN-канонике). | MVP: trigram по `name` + `team_aliases`; позже `search_text` (имя + все переводы, lower/unaccent) с GIN `gin_trgm_ops` или внешний поиск |
| 33 | **Срок хранения устаревших прогнозов** (`pre_match` без picks) и `prediction_scorelines`. | 7 дней после замены прогноза; `locked` и текущий хранятся всегда |
| 34 | **TTL live-страниц и CDN для гостевых страниц.** | Live: Redis 5–15 с, без CDN; публичная лента гостя: `s-maxage` 10–60 с; пересматриваем после замеров |
| 35 | **Порог партиционирования.** | Ориентир: таблица > 50–100 млн строк или обслуживание (VACUUM, индексы) занимает часы; решение принимаем по `pg_stat_statements`/размерам, а не заранее |

**Кратко, что выбрано (2026-11-25):**

- **№ 29** — `source_providers.config.source_locale`; русское имя из источника идёт во временный `name` + `name_i18n[source_locale]`, EN-имя задаётся на ревью, `slug` — после него.
- **№ 30** — UI на `ru`, fallback `en`; локаль: `users.locale` → cookie → `Accept-Language` → `ru`; URL без языкового префикса. В БД для этого добавлено `users.locale`.
- **№ 31** — провенанс переводов не ведём; ИИ заполняет только пустые ключи; `entity_translations` — позже.
- **№ 32** — поиск: trigram по `name` + `team_aliases`; `search_text` с GIN — позже.
- **№ 33** — устаревшие `pre_match`-прогнозы без picks удаляются через 7 дней после замены; `locked` и текущий хранятся всегда.
- **№ 34** — live: Redis 5–15 с, без CDN; гостевая лента: `s-maxage` 10–60 с.
- **№ 35** — партиционирование не делаем; порог — таблица > 50–100 млн строк или обслуживание в часах, решение по `pg_stat_statements`.

## Пересмотр после реальных данных

Что стоит проверить первым, когда появятся реальные данные источника, и где скорректировать defaults без перестройки схемы:

- **Статистика (п. 3, 8):** какие метрики и xG реально отдаёт источник → какие поля вынести из `extra jsonb` в колонки; нужен ли shot-level.
- **Маппинг (п. 13, 14):** доля несматченных команд/игроков, нужна ли админка слияния раньше, чем планировали; приоритеты провайдеров.
- **Плей-офф и форматы (п. 2, 23–26):** как источник отдаёт сетки, этапы и стыки → правила в `stages.rules`, создание `ties` заранее или по факту.
- **Таблицы (п. 5):** тай-брейки и штрафные очки в реальных чемпионатах.
- **Рейтинг (п. 4, 11, 12, 20):** история рейтинга, замены picks, политика никнеймов, правило для товарищеских — по результатам тестирования с пользователями.
- **Мультиязычность и объём (п. 27–35):** доля сущностей без EN-имени от источника, нужен ли провенанс переводов, реальные размеры `prediction_outcomes`/`match_events`, фактические медленные запросы и пороги партиционирования; нужен ли `team_season_stats` раньше «позже».
- **Время (п. 18):** какой часовой пояс для «дня» нужен при втором-третьем чемпионате.
