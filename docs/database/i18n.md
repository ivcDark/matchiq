# MatchIQ — мультиязычность сущностей

Часть [схемы БД](README.md). **Статус:** паттерн выбран и принят (решение № 27 в [open-questions.md](open-questions.md)); миграции и модели созданы 2026-11-25 (`web/database/migrations`, трейт `App\Models\Concerns\HasI18nNames`).

## Требования

- Переводимые сущности: страны, соревнования, команды, стадионы, игроки, тренеры, судьи (+ справочник рынков). Подписи этапов и туров («15-й тур», «1/8 финала») — не данные, а интерфейс (см. ниже).
- **Каноническое имя в БД — английское**, в основной колонке `name`. Оно же ключ для маппинга источников, логов и админских инструментов.
- Переводы (RU, ES, …) появляются позже — вручную или генерацией ИИ. Набор языков растёт без миграций.
- Мультиязычность **не должна утяжелять запросы** горячих страниц (главная лента, страница матча): ни лишних JOIN, ни отдельных запросов за переводами.

## Сравнение вариантов

| Вариант | JOIN на горячем пути | Плюсы | Минусы |
|---------|----------------------|-------|--------|
| **A. `entity_translations`** (`entity_type`, `entity_id`, `locale`, `field`, `value`) | да, на каждую сущность в выдаче (2 команды + лига + стадион + судья на матч) или дополнительный запрос `WHERE (type,id) IN …` | одна таблица на всё; есть место под provenance (`source`, `status`), длинные поля | полиморфная связь без FK; EAV: тяжело фильтровать и сортировать; N×JOIN или «второй запрос» на каждой странице; кэш — отдельная забота |
| **B. jsonb `name_i18n` на сущности** | **нет** — перевод едет вместе со строкой | один SELECT; пишется и читается атомарно; новая локаль — просто новый ключ; индексы не нужны; TOAST не страшен (десятки байт) | денормализация; нет аудита «кто и когда перевёл»; поиск/сортировка по локали требуют отдельных мер |
| **C. `team_translations`, `player_translations`, …** | да, JOIN или eager-load на каждую | FK и типизированные колонки, можно хранить любые поля | 7+ таблиц и миграций; JOIN'ы на горячем пути; избыточно для одного-двух полей |

## Выбор: гибрид «B сейчас, A при необходимости»

**Основной паттерн (MVP) — вариант B.** На каждой переводимой сущности:

- `name varchar` — каноническое **английское** имя (источник правды, `NOT NULL`);
- `name_i18n jsonb NOT NULL DEFAULT '{}'` — переводы: `{"ru": "Зенит", "es": "Zenit"}`. Ключ `en` **не пишем** (английский — это `name`);
- там, где в UI показывается короткая форма или город — парные `short_name_i18n`, `city_i18n` (только `teams`, `competitions`, `venues`; остальным не нужно).

Читаем так: **локаль → `en`** (`name_i18n[locale] ?? name`). Цепочка fallback задаётся конфигом (`requested → базовый язык (pt-br → pt) → en`), в БД не хранится и данными не кодируется.

**Расширение (позже, по необходимости) — вариант A как write-side.** Если понадобятся провенанс и ревью («перевёл ИИ, не проверено», кто и когда правил) или переводы длинных полей (описание клуба, биография), вводим `entity_translations` (`entity_type`, `entity_id`, `locale`, `field`, `value`, `source`: `manual` \| `ai` \| `provider`, `status`: `draft` \| `approved`, `updated_by`, UNIQUE по первым четырём). Тогда она — **источник правды**, а `name_i18n` на сущностях — её денормализованная проекция (обновляется при сохранении перевода). Горячий путь читает по-прежнему только jsonb: схема чтения не меняется. Вариант C не берём.

### Почему так

1. **High-read UI.** Одна карточка матча на главной — это 2 команды, лига (и стадион/судья на странице матча). Вариант A давал бы +3–5 JOIN или запрос на каждую выдачу; вариант B — **ноль**. Лента из 200 матчей остаётся «матчи + прогноз + eager-загрузка команд по `whereIn`» ([performance.md](performance.md#горячие-пути-и-бюджет-запросов)).
2. **Cache-friendly.** Redis-агрегаты (лента дня, страница матча, таблица) хранят **локаленезависимый** payload: имена приходят с `name` + `name_i18n`, а выбор языка происходит при сериализации ответа. Один кэш обслуживает все локали; не нужен ключ `…:{locale}` и инвалидация ×N.
3. **Малый объём.** Переводов на сущность — единицы, строк — десятки тысяч; jsonb укладывается в десятки байт на строку и не раздувает ни индексы, ни heap.
4. **Новая локаль без миграции.** Добавили код локали в конфиг и заполнили ключи.
5. **Обратимость.** Проекция из `entity_translations` в jsonb — тривиальная задача, поэтому выбор B не закрывает путь к A.

## Какие сущности и поля

| Таблица | Колонки | Заметки |
|---------|---------|---------|
| `countries` | `name`, `name_i18n` | «Russia» / «Россия» |
| `competitions` | `name`, `name_i18n`, `short_name`, `short_name_i18n` | «Russian Premier League» / «Российская премьер-лига»; короткий код в чипе (`РПЛ`) |
| `teams` | `name`, `name_i18n`, `short_name`, `short_name_i18n`, `city`, `city_i18n` | `short_name` — «CSKA» / «ЦСКА» |
| `venues` | `name`, `name_i18n`, `city`, `city_i18n` | |
| `players` | `name`, `name_i18n` | `first_name` / `last_name` остаются каноническими (EN); переводится только отображаемое полное имя |
| `coaches`, `referees` | `name`, `name_i18n` | у `referees` город — не переводим |
| `market_types` | `name`, `name_i18n` | вместо прежнего `name_ru` |
| `market_type_outcomes` | `label`, `label_i18n` | вместо прежнего `label_ru`; EN-подпись «Home win» в `label` |

**Не переводим в БД:**

- `slug` — всегда латиница, создаётся из EN-имени и **не меняется** (адреса — по `id`);
- `stages.name`, `rounds.name`, `stage_groups.name`, `standing_zones.label` — подписи формата строятся **интерфейсом** по `type` / `code` / `number` через языковые файлы приложения («Matchday 15» / «15-й тур», `QF` → «1/4 финала»); `name` хранит EN-значение как fallback и для нестандартных названий. Если источник начнёт отдавать нестандартные локализованные названия этапов, добавляем `name_i18n` на них точечно (это не ломает схему);
- `match_previews` и другие сгенерированные тексты — это уже контент по локали (`match_previews.locale`), а не перевод сущности;
- `team_aliases` — это ключи сопоставления источников, а не отображаемые имена (хотя русские алиасы там тоже могут жить).

## Правила и ограничения

- `CHECK (jsonb_typeof(name_i18n) = 'object')`; ключи — коды локалей из конфига (`ru`, `es`, `pt-br`; строчные, BCP 47), значения — непустые строки ≤ 255 символов. Валидирует приложение (форм-реквест/кастомный cast), БД страхует типом.
- **Коллектор пишет только `name` (EN)** и никогда не трогает `*_i18n`: upsert по `external_ids` исключает эти колонки из `DO UPDATE SET`. Переименование источника в EN не стирает переводы.
- **Переводы пишутся точечно**, без перезаписи объекта целиком: `name_i18n = name_i18n || jsonb_build_object('ru', :value)`.
- **ИИ-перевод заполняет только отсутствующие ключи** и не перезаписывает значения, поставленные вручную (в MVP провенанса нет; защищает правило «пустое — ИИ, заполненное — человек»).
- Сидирование моков: 16 клубов РПЛ (id 1–16) получают EN в `name` и текущие русские подписи в `name_i18n.ru` (см. решение № 19).
- Eloquent: трейт `HasI18nNames` с акцессором `localized('name', $locale)`; API-ресурсы отдают **уже выбранное** значение (`name`) — фронтенд про jsonb не знает.

## Как читать

- **Горячий путь (карточки, списки, шапки):** `SELECT id, name, name_i18n, …` и выбор языка в PHP (`$i18n[$locale] ?? $name`). SQL остаётся без `COALESCE`, кэш — локаленезависимым. Выбираем только нужные колонки, не `SELECT *`.
- **Сортировка по локализованному имени** (алфавитные списки команд/игроков): для коротких списков — в PHP (`Collator`); для больших — SQL `ORDER BY COALESCE(name_i18n->>:locale, name) COLLATE "ru-x-icu"` и, если выяснится, что запрос частый, выражение-индекс на эту локаль. Не в MVP.
- **Поиск.** В MVP: `name` (trigram `pg_trgm`) + `team_aliases`. Когда понадобится поиск по переводам — `search_text` (имя + все переводы, lower/unaccent), поддерживаемый сервисом записи, с GIN-индексом `gin_trgm_ops`; либо внешний поисковый движок (не в MVP).
- **Локаль запроса:** `users.locale` → cookie → `Accept-Language` → дефолт `ru`; URL без языкового префикса в MVP (решение пересматривается при SEO-мультиязычности).
